## Изменения контракта

`docs/storage-contract-v1.md`:

- наследование аннотации проверяет существование авторов и установки-источника, но не
  активность исторической установки — восстановление не переписывает историю;
- повторная регистрация корня и привязка к неизвестному пользователю — доменные ошибки;
- цель, заменённая после `synced` каталогом или reparse-точкой, переводит задание в
  `error`, а не остаётся ложно `synced`;
- `check_local_path` проверяет resolved цель, поэтому symlink не обходит запрет;
  документные корни и цели дополнительно запрещают symlink/reparse;
- повреждённый сохранённый JSON — ошибка хранилища, а не `JSONDecodeError`.

## Перепроверено по поведению

- `file_locations`: уникальная каноническая цель, `confirmed_revision`/`confirmed_hash`,
  проверка соответствия root+relative при `validate_copy`.
- Поколение задания совпадает с ревизией документа, ожидаемые прежние хэши сверяются;
  частично заменённый собственный файл не считается внешней правкой.
- После `synced` удалённый current-файл восстанавливается событием `missing_restored`,
  подменённый — конфликтом с сохранением байтов до 8 МиБ.
- `rebind_restored_copy` отклоняет корни-предки/потомки старых и пересечения между новыми.
- `undo` в открытом JSON ограничен известными полями; произвольные снимки не попадают
  в экспорт; `interaction_events` ограничены 2000 со счётчиком вытесненных; heartbeat
  не создаёт review-снимок.
- Гонка создания архива фиксирует конфликт, а не перезапись.

## Остаточные наблюдения (политика, не дефекты этого пакета)

- `register_root` по-прежнему разрешает вложенные/пересекающиеся активные корни;
  непересечение принудительно только при восстановлении. Коллизий целей это не даёт:
  у записи один корень, а относительные имена генерируются из `recording_id`.
  Решение о резервировании корней при регистрации — вопрос П2.
- Путь БД через junction к локальному fixed-диску допускается: проверяется resolved
  диск. Документные корни и цели reparse запрещают.
- Архивы после `synced` по-прежнему не восстанавливаются автоматически (сознательная
  неизменяемость). Расхождения теперь видны через `documents.verify_files`, но
  автопочинки нет by design.
- Реальный сбой питания, сетевые и облачно-синхронизируемые ФС не проверялись;
  облачная синхронизация на fixed-диске по пути надёжно не определяется.

## Отчёт проверки файлов (`documents.verify_files`)

Добавлена отдельная операция отчёта: `verify_files(store, root_id, root_path)`
сверяет `file_locations`, `document_versions` и файлы всех поколений корня,
включая архивы, которые больше не проходят через `materialize_pending`.
Есть также CLI-команда `python -m tools.verify_document_files --db <путь-к-БД>
--root-id <UUID-корня> --root <путь-к-корню>`; она открывает БД read-only,
печатает JSON в stdout и завершает работу с кодом 0 (согласовано), 1 (расхождения)
или 2 (ошибка проверки).

- Только чтение: файлы не заменяются, каталоги и lock-файл не создаются, БД не
  меняется, отсутствующие архивы не восстанавливаются.
- Обе стороны сверки: запись реестра → ожидаемый хэш версии → файл на диске,
  а также версии документа → наличие записи в реестре.
- Статусы: `ok`, `missing`, `modified`, `unconfirmed`, `unresolved_conflict`,
  `invalid_target`, `unreadable`, `registry_mismatch`, `registry_incomplete`,
  `unknown_document`; для каждого файла отдаются ожидаемый/наблюдаемый SHA-256,
  размер, ревизия, поколение и последнее состояние очереди.
- Итог: `consistent`, `checked`, `counts` и полный список `entries`.
- Запросы SQLite читаются в одном read-снимке; параллельная материализация или
  внешний редактор всё ещё могут изменить файлы во время проверки. Для устойчивой
  сверки запускайте отчёт при простое очереди и внешних редакторов.
