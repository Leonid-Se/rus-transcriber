## Что добавлено

- `recordings.py` разделяет известные поля результата worker на transcript- и
  review-снимки, сохраняет runtime metadata в `quality.runtime` и отклоняет
  неизвестные верхнеуровневые поля.
- Для отсутствующих/повторных ID сегментов и слов назначаются UUIDv5 от
  `recording_id` и позиции. Повтор с тем же ID записи формирует те же снимки,
  поэтому operation replay не меняет хэш параметров.
- `commit_worker_result` вызывает атомарный API П1: commit записи, снимков,
  версии документа и outbox. Он требует открытый Store, заранее зарегистрированный
  корень, контекст и стабильные IDs операции/записи. Materializer вызывается
  отдельно.
- `install.ps1` включает новый runtime-модуль. Контракт и этот handoff уточняют
  границу текущего шага.

## Не подключено и ограничения

Это библиотечный адаптер, не рабочий backend: `core.py`, `worker.py`, `server.py`,
`rt.py`, `transcript.py`, `review_pack.py` и `conspect.py` пока не маршрутизируют
операции через SQLite. Пользовательское переключение backend отсутствует.
Проверено только выбранное синтетическое представление worker, не весь набор
вложенных полей и режимов pipeline.

До подключения runtime нужно закрыть файловые обходные писатели, определить
единый resolver и доступ без job, связать worker с явным API, авторство/инициатора
с установкой и UI имени, а также проверить sidecar-пути, корни, конфликт внешних
файлов и ошибки/повторы materializer. До этого SQLite backend нельзя включать
для пользователя. Старые записи и миграция не затрагивались.

Дополнение: правила общего sidecar-корня и имён целей реализованы следующим
шагом и описаны в [`2026-11-16-p2-path-handoff.md`](2026-11-16-p2-path-handoff.md).

Проверки выполнены в отдельном временном sandbox с синтетическими данными.
