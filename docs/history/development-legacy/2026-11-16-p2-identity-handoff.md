## Изменения

- `paths.STATE_DB` задаёт `DATA_DIR/state.sqlite3` без создания файла.
- `storage.initialize(..., initial_display_name=...)` может создать схему,
  локального пользователя и installation ID одной транзакцией. Старый вызов
  без аргумента сохраняет поведение П1.
- `Store.current_identity()` требует ровно одну активную привязку и не выбирает
  автора при неоднозначности.
- `recordings.initialize_store()` и `recordings.open_store()` дают явные API:
  первая только создаёт новую БД, вторая только открывает существующую.
- `settings.user_display_name` / `set_user_display_name` работают через БД;
  имя не копируется в `config.json`. Смена имени не меняет уже захваченные
  снимки контекста.

## Проверки и ограничения

Синтетические тесты проверяют расположение БД, явное создание, начальное пустое
имя, стабильность identity после повторного открытия, rename без config-копии,
неизменность ранее снятого имени, отказ от невалидного имени и неоднозначной
активной привязки.

Ни один UI или runtime writer пока не использует эти API. Это не миграция
существующих данных и не активация SQLite backend в приложении. Проверки
выполняются на синтетике и изолированном DATA_DIR.
