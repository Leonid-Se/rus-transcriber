## Назначение и граница

`storage.py` и `documents.py` реализуют экспериментальный библиотечный фундамент
П1а–П1в: SQLite-снимки и авторство, версии документов, очередь materialization,
файловый реестр, неизменяемые архивы, конфликты и восстановление после backup.
Прототип не интегрирован в `core.py`, `server.py`, `rt.py` или обычный каталог
данных программы; миграции нет. Это не production API и не текущий формат импорта.
Использовать синтетические базы и корни, не рабочие пользовательские данные.

Подробный контракт: [`storage-contract-v1.md`](storage-contract-v1.md).

[`2026-11-16-p1a-reaudit.md`](2026-11-16-p1a-reaudit.md).

## Проверка файлов и архивов

Из корня клона команда:

```powershell
python -m tools.verify_document_files --db <путь-к-БД> --root-id <UUID-корня> --root <путь-к-корню>
```

Для заданного зарегистрированного корня она сравнивает `file_locations`,
подтверждённые хэши в `document_versions` и состояние файлов на диске. Проверяются
current-цели и архивные пути всех поколений. Также выявляются отсутствующие строки
реестра и невозможные/нечитаемые цели.

Команда открывает SQLite в read-only режиме (`mode=ro`, `query_only=ON`), не создаёт
каталоги или lock-файл, не изменяет БД и ничего не восстанавливает. Она печатает
JSON:

- `consistent`, `checked`, сводные `counts`;
- `entries` с записью, типом/путём файла, ревизией/поколением, состоянием outbox,
  ожидаемым и наблюдаемым SHA-256, размером и статусом.

Код завершения: `0` — все записи `ok`; `1` — есть расхождения; `2` — проверка
не выполнена (ошибка схемы/доступа/пути). Отчёт не фиксирует конфликт в БД и не
переписывает внешний файл — расхождение предназначено для ручного решения. Проверка
использует единый read-снимок SQLite. Файловая система не блокируется: не запускайте
одновременно с materializer/редактором, иначе файлы могут измениться в ходе прохода.

Статусы:

| Статус | Значение |
|---|---|
| `ok` | файл совпадает с подтверждённой версией |
| `missing` | подтверждённый файл отсутствует |
| `modified` | файл есть, но SHA-256 отличается |
| `unconfirmed` | строка есть, но поколение ещё не подтверждено materializer-ом |
| `unresolved_conflict` | цель уже отмечена конфликтной |
| `invalid_target` | путь ведёт через reparse/symlink или цель не обычный файл |
| `unreadable` | файл нельзя прочитать |
| `registry_mismatch` | канонический путь/подтверждённый хэш расходится с данными БД |
| `registry_incomplete` | версии/outbox есть, соответствующая цель отсутствует в реестре |
| `unknown_document` | реестр ссылается на отсутствующую ревизию документа |

## Следующие решения перед продолжением

1. Перед дальнейшими изменениями сверять `git status`, HEAD и полный diff; этот пакет
   уже зафиксирован отдельным коммитом `cd21152` в `architecture-p1a`.
2. Не подключать прототип к приложению без отдельного плана API, расположения БД,
   резервирования корней, миграции, восстановления и тестов взаимодействия с
   существующими данными.
3. Перед интеграцией решить, должны ли активные корни запрещать вложенность уже
   при `register_root` (сейчас непересечение обеспечивается только при rebind backup).
4. Отчёт использует единый read-снимок SQLite, но файловый набор не блокируется;
   стабильное сравнение диска требует простоя materializer и внешних редакторов.
5. Архивы намеренно не восстанавливаются автоматически. `verify_files` показывает
   расхождения, но решение о ручном восстановлении/экспорте и процедуре сверки после
   внешней замены должно остаться явным; не превращать отчёт в автопочинку без
   отдельного требования.
6. После выбора политики обновить контракт, тесты и инструкции запуска; сверить
   README, установщик и фактическую интеграцию. Не представлять dev-only команду
   как часть обычного runtime.
